**Test structure -- 10 scenarios (AC1 through AC10) mapping every section 11 acceptance criterion:**

AC1 -- **Phase-gate 403**: Use `withSeedPage` to create a page for the leader role, navigate to `/pvp/lobby`. Verify the page renders (the lobby should be accessible for a `working`-phase team). Then test that the phase gate fires for a team below `working`: either (a) seed a team at `literature_review` phase and verify its PvP API calls return 403, or (b) skip the true 403 test if seeding a second team is impractical and instead verify the leader's PvP routes respond 200. If skipping, document the gap in a comment. Per GATE-01/D-29: every PvP route must gate server-side.

AC2 -- **No-base guard**: Verify that a team with no placed base cannot match. Either seed the "E2E Test Lab" team to have zero `team_shop_buildings` (temporarily), call GET `/api/pvp`, and verify the response indicates `noOpponent` or no match available. Restore buildings after. Per GATE-02/D-07.

AC3 -- **Matchmaking pools same-class, working+ phase**: Call GET `/api/pvp` and verify the response includes `opponent` data (team name, trophy count, building count). Verify the opponent is not the attacker's own team. Per RAID-01/D-07.

AC4 -- **Refind excludes already-shown opponent**: Call POST `/api/pvp` with `{action: "refind", shownBaseIds: [...]}` including the previously returned opponent's ID. Verify the response returns a DIFFERENT opponent id (or `noOpponent` if no other eligible base exists, which is acceptable). Per RAID-02/D-07.

AC5 -- **Full raid E2E: match -> start -> cast -> results**: Execute the full raid flow:
  1. POST `/api/pvp` with `{action: "start_raid"}` using the matchmaking opponent
  2. Verify response includes `raidId`, `defenderBase` (buildings), `startedAt`
  3. Navigate to `/pvp/battle/{raidId}`
  4. Verify the BattleScreen renders with defender grid, spell bar, timer HUD
  5. POST to `/api/pvp/{raidId}/action` with `{spellId, x, y, clientTs}` (cast a spell)
  6. Wait for timer expiry or verify `completeRaid` fires
  7. Verify results screen shows `percentDestroyed` and `trophyDelta`
  Per RAID-03/04/05/D-19/D-02.

AC6 -- **Daily quota exhaustion**: Execute 3 raids (or the configured `MAX_RAIDS_PER_DAY`). After the 4th start attempt, verify the API returns a quota-exhausted error. Then verify refind quota similarly. Per TROPHY-05/D-17.

AC7 -- **Catalog display names**: Verify that building and spell display names in the loby and battle UI come from catalog rows, not derived key-casing. Assert that a building name like "power_plant" renders as its catalog name (e.g. "Power Plant") not "Power Plant". Per RAID-06/D-09.

AC8 -- **Meter tiers display**: Navigate to `/pvp/lobby`. Verify the Spell Power Meter component renders with tier label and multiplier. Assert that the displayed tier matches the team's daily task count range (0=Dormant x0.5, 1-2=Active x1.0, 3-4=Charged x1.5, 5+=Overcharged x2.0). Use an API call to GET `/api/pvp/spell-power` to confirm the tier. Per METER-01/02/03/D-18.

AC9 -- **Trophy gain/loss**: Execute a full raid that achieves >=30% destruction and verify `trophyDelta > 0` and `<= 10`. If feasible, also execute a low-destruction raid (by casting only one spell that does minimal damage) and verify `trophyDelta < 0`. The loss path is behind `TROPHY_LOSS_TODO=true` -- if the stub is still active, the test still verifies the delta calculation matches expected values. Per TROPHY-01/02/03/D-14/D-15.

AC10 -- **Symmetric defender loss**: After a completed raid, verify that the `PvpTrophies` record for the defender was decremented by the same `trophyDelta` the attacker gained. Use `e2eDb.pvpTrophies.findUnique` to read defender trophies before and after the raid. Per TROPHY-06/D-16.
