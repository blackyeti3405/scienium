# scienium

A browser game where student teams run a science-fair research lab. Teams read
real papers, take generated quizzes on them, discover sources and prior art,
plan and run experiments, and present at a fair. Teachers get a roster, progress
views, and moderation tools.

The goal is narrow and practical: most students meet the research process for
the first time as a deadline. scienium turns the same process — literature
review, a defensible question, a plan, data, a presentation — into something
with structure and feedback, so the science-fair project is the curriculum
rather than the homework.

**Status: pre-pilot.** v0.82.0, heading for a real classroom pilot. It runs end
to end, and there is deliberate deferred work tracked in
[`docs/TODO.md`](docs/TODO.md). Not deployed to production yet.

## What's here

A pnpm monorepo.

| Path | What it is |
|---|---|
| `apps/web` | The application — Next.js 15 App Router, all routes and features |
| `packages/shared-types` | Types shared across the workspace; build this first |
| `packages/config` | Shared tool configuration |
| `infra/` | Seed data (ISEF categories, lab types, buildings) and local Docker Postgres |
| `art/` | The pixel-art pipeline — sprites are generated by code, not hand-drawn files |
| `docs/` | Architecture, spec, setup, changelog, ADRs, runbooks |

`apps/web/app` is organised by route group: `(auth)`, `(dashboard)`,
`(onboarding)`, `(public)`, `(teacher)`, plus `api/`.

**Stack.** Next.js 15 + TypeScript, Prisma + PostgreSQL, Clerk for auth, the
Anthropic API for the LLM features (paper metadata, quizzes, chat, relevance
checks), Cloudflare R2 for uploads, Vitest and Playwright for tests.

**Data model.** Everything is team-scoped: School → Class → Team → TeamMember.
Every query and mutation is scoped to the caller's authenticated team.

## Reading the code

If you are reviewing this rather than running it, these are the places where the
actual thinking is:

- [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) — how the system fits together,
  and why.
- [`docs/SPEC.md`](docs/SPEC.md) — what the product does, feature by feature.
- [`docs/architecture/`](docs/architecture/) — ADRs for the decisions that were
  hard to reverse: team/class ownership, paper processing, feature boundaries.
- [`docs/CHANGELOG.md`](docs/CHANGELOG.md) — the real development history.
- [`apps/web/lib/`](apps/web/lib/) — the server-side logic. Authorization,
  LLM calls, rate limiting, and the game systems live here rather than in route
  handlers.

A note on the LLM features: they are cost-constrained on purpose. Prompt caching
and local computation are preferred over extra API calls, there is a per-team
daily cap on the expensive paths, a daily spend alert, and a global kill switch
that stops every paid provider call without a deploy.

## Running it

Full instructions, including the database and auth setup you will need, are in
[`docs/SETUP.md`](docs/SETUP.md). The short version:

```bash
pnpm install
pnpm --filter @scienium/shared-types build
cp apps/web/.env.example apps/web/.env.local          # then fill it in
pnpm --filter web exec prisma migrate deploy          # apply all migrations
pnpm dev
```

You need a Postgres database (Supabase or the local Docker Compose file in
`infra/`), a Clerk application, and an Anthropic API key. The scholarly-source
APIs work without keys at a lower rate limit.

### Checks

Run from the repo root, in order:

```bash
pnpm --filter @scienium/shared-types build
pnpm --filter web check:integrity
pnpm --filter web typecheck
pnpm --filter web lint
pnpm --filter web build
pnpm --filter web test:e2e
```

CI runs the first five on every PR. The Playwright suite runs against a real
logged-in browser and needs a database and test credentials; it runs on PRs as a
smoke lane and nightly in full.

There are 207 Vitest files, 38 Playwright specs, and 89 migrations.
